# 03b — 产品化机制通用原则

跨场景的产品化原则。回答一个问题: 为什么功能齐了, 程序能跑了, 但产物看起来仍像后台 / 内部工具 / engineering demo, 而不像成熟上线产品?

工程成立和产品成立是两件不同的事。`opc-delivery` 同时要这两个。

## 工程成立 vs 产品成立

两者同等地位, 缺一不算完成。

| | 工程成立 | 产品成立 |
|---|---|---|
| 检查面 | 真实可登录、可操作、数据持久化 | 用户能识别产品姿态、IA 主次正确、不像后台/内部工具 |
| 验收方 | lint / typecheck / test / build / Browser HTTP 200 / API 溯源 | 截图给陌生人能识别这是什么产品 + IA 入口分布合理 + 没有 dashboard 化退化 |
| 失败信号 | 测试红、build 报错、刷新数据丢、API 返回 500 | 看着像后台、首页全是 KPI 卡和能力入口、一级 nav 摆 12 项 |
| 错误诊断 | 读 stack trace / 改实现 | 重排 IA / 移动入口位置 / 升降级 |

工程成立失败 → 不能跑。
产品成立失败 → 能跑, 但用户觉得像内部工具或半成品 demo。

后者损害不显性, 但累计起来就是"为什么 AI 生成的产品总是看着不像真产品"。

## 产品姿态判断

每个产品归属于一个主姿态。**主姿态决定 IA 默认骨架, 不要套错壳层。**

### 7 类姿态

| 姿态 | 子类型示例 | 主任务 | 默认 IA 骨架 | 反模式 |
|---|---|---|---|---|
| **内容消费** | reading / video / feed / 听书 / 短视频 / 学习材料 | 连续消费内容 | 内容主体占首屏, 导航极简 | 摆 dashboard 卡, 把"消费"做成"管理" |
| **SaaS-工作台** | 协作平台 / 客服系统 / 项目管理 / 设计协作 | 处理工单 / 推进事务 | 列表 + 详情 + 侧栏, 任务流为主 | 把工作台做成首页 marketing |
| **专业工具** | IDE / 设计软件 / 数据库客户端 / 终端 | 单次完成专业任务 | 工作区主体, 工具栏环绕 | 把工具做成步骤向导 |
| **学习产品** | 课程 / 题库 / 训练营 / 语言学习 | 完成一个学习路径 | 路径进度 + 当前课时主体 | 摆得像知识库后台 |
| **社区** | 论坛 / Q&A / 微博类 / 评论站 | 看别人 + 发自己 | timeline / feed + 发布入口高曝光 | 做成 dashboard 看自己的数据 |
| **AI 助手** | chat / agent / 文档助手 | 对话或多轮交互 | 对话主体占首屏, 历史侧栏 | 把对话框做成普通搜索框 + 大堆推荐 |
| **其它** | 工具型小程序 / 单一目的页面 / 不明确分类 | 单一任务 | 任务主体占首屏 | 强行套通用 app 壳层 |

### 选主姿态 + 次要姿态

强制选 1 个主姿态, 允许标 1 个次要姿态。**不允许"什么都是"。**

- 例: Notion = 主姿态: 专业工具(创作) + 次要: SaaS-工作台
- 例: 微信读书 = 主姿态: 内容消费(reading) + 次要: 社区
- 例: Linear = 主姿态: SaaS-工作台 + 次要: 无

理由: 一旦"什么都是", IA 骨架就无主见, 退化成通用 app 壳层。

### 反例排除写法

写姿态时必须给反例排除, 防止糊。模板:

```
主姿态: 内容消费 (reading)
理由: 用户主任务是连续阅读, 不是配置或管理
反例排除:
- 不是 SaaS-工作台: 因为用户不是来处理事务的
- 不是工具: 因为不是单次完成任务后离开, 而是反复回来
```

## 竞品调研

方案阶段强制做。产物 `.opc/solution/competitor-survey.md`。

### 步骤

1. 基于用户需求列 2-3 个同品类成熟上线产品(例: 用户要做读书 app → 微信读书 / Kindle Web / 多看)
2. 对每个产品抓取(拿到啥用啥):
   - **优先级 1**: `bash + curl` 或 `WebFetch` 拿 marketing landing page (多数产品官网 SSR, 能拿到)
   - **优先级 2**: `webapp-testing` 起 Playwright 拿未登录态截图(需本地 Playwright 可用)
   - **兜底**: 代理从知识库写 IA 文字描述(产品名 + 描述具体到一级 nav 项)
   - VIP 功能不需要; marketing 页 + 未登录态足够推断姿态和首屏
3. 输出 `competitor-survey.md`:

```markdown
# 竞品调研 vs <需求>

| 产品 | 姿态推断 | 一级导航 | 首屏主信号 | 学什么 | 不学什么 |
|---|---|---|---|---|---|
| 微信读书 | 内容消费(reading) | 书架 / 发现 / 故事 / 我 | 上次未读位置 + 推荐书架 | 阅读连续性 | "故事" tab 抢戏 |
| Kindle Web | 内容消费(reading) | 首页 / 图书馆 / 设备 | 上次阅读 + 购买推荐 | 极简阅读体验 | 商店化太重 |
| 多看 | 内容消费(reading) | 推荐 / 书架 / 商店 | 推荐流 | 中文排版细节 | 商店主导首屏 |

## 总结
- 共性: 主姿态都是 reading; 首屏都有"上次未读 + 发现"双信号
- 我的选择: 学微信读书的"上次未读位置优先 + 书架次之"; 不学多看的"商店主导"
```

### 拿到啥用啥

| 工具 | 拿到啥 | 用途 |
|---|---|---|
| `curl -sL <url>` | marketing landing page HTML | 看 nav 文本, 推断一级导航 |
| `WebFetch` | 同上 + AI 提取 | 自动概括产品定位和功能列表 |
| `webapp-testing` + Playwright | 真实未登录截图 | 看首屏视觉权重 |
| 代理知识库 | 文字描述 | 兜底, 必须写出产品名 + 具体 nav 项 |

竞品截图回流走 [09-runtime-budget.md](09-runtime-budget.md#截图回流) 的 thumb 约束。

## 首屏主信号

定义: **用户进来一眼锁定的那个东西**。不是产品能力的总展示, 不是 marketing slogan, 不是公告栏。

### 写法约束

必须能描述成"可截图的具体画面", 不能写口号。

| 反面例子 | 正面例子 |
|---|---|
| 突出核心价值 | 进入即落到上次未读章节, 标题占首屏 40% 高度, 没有 KPI 卡 |
| 帮助用户高效完成任务 | 任务列表占左侧 60%, 当前任务详情占右侧 40%, 顶部无 marketing |
| 展示产品能力 | 对话框占首屏中央 60%, 历史在左侧抽屉, 无功能瀑布流 |
| 让用户感受智能 | (这就是口号, 永远不接受) |

### 反 dashboard 化承诺

如果不是 dashboard 类产品, 必须明确说明首屏不是:
- "N 个 KPI 卡片 + M 个能力入口"
- "上半屏 hero + 下半屏功能矩阵"
- "公告栏 + 推荐栏 + 数据栏"

如果就是 dashboard 类(也合法), 也要说明:
- 信息密度的优先级是什么
- 哪几个指标是"真主信号", 哪些是"参考信息"
- 不允许"放 12 个 KPI 卡, 全都同等大小"——必须排序

### 同品类对比

写首屏时必须给一句同品类对比:

```
同品类成熟产品 <名字> 的首屏大致是 <一句描述>,
我的设计在 <哪些点> 像, 在 <哪些点> 故意不同, 原因是 <...>
```

## 能力升降级

把所有规划的能力分到 4 个曝光层级。

### 4 个曝光层级

| 层级 | 含义 | 位置 |
|---|---|---|
| **高曝光** | 用户主任务承接, 首页主区或一级导航可见 | 一级导航 / 首页主区 |
| **中曝光** | 主任务支撑, 二级可达 | 二级 tab / 详情页内 / 顶部次级导航 |
| **低曝光** | 配置 / 偶尔用 / 主管/管理员用 | 设置子项 / 用户菜单 / 详情页深层 |
| **仅上下文** | 不是页面, 是操作 | 行内按钮 / 悬浮工具栏 / 右键菜单 / 详情页里的 action |

### 数字约束

| 约束 | 类型 | 说明 |
|---|---|---|
| 高曝光数 ≤ 5 | **硬卡** | 一级导航最多 5 项, 超过 = 用户找不到 / 后台感 |
| 低曝光 + 仅上下文 比例 ≥ 30% | **软约束** | 不到 30% 必须写理由, 防止"全部摆出来" |

硬卡 = handoff-lint 不通过, 必须修。
软约束 = 写理由就放过(理由会被 3C 独立 reviewer 看到)。

### 案例: AI 客服平台

PRD 抽出 20+ 能力, 升降级后:

| 能力 | 层级 | 位置 | 理由 |
|---|---|---|---|
| 工单列表 | 高曝光 | 一级导航首位 / 首页主区 | 客服主任务就是处理工单 |
| 工单详情 | 高曝光 | 列表点入, 不另设导航 | 主任务的承接 |
| 队列 / 分派 | 高曝光 | 一级导航次位 | 主管的主任务 |
| 知识库 | 中曝光 | 工单详情侧栏 + 二级 tab | 辅助主任务 |
| 智能建议回复 | 中曝光 | 工单详情侧栏 | 辅助, 不独立页 |
| 报表 | 中曝光 | 一级导航末位 | 主管用, 客服日常不用 |
| 转人工 | 仅上下文 | 工单详情按钮 | 不是页面, 是操作 |
| 标签管理 | 低曝光 | 设置子项 | 配置类, 长期不动 |
| 通知模板 / SLA / 工作时段 | 低曝光 | 设置子项 | 一次配置 |
| 团队 / RBAC / 角色 | 低曝光 | 设置子项 | 管理员偶尔用 |
| 审计日志 | 低曝光 | 设置 > 安全 | 出事才看 |
| 计费 / 集成 webhook | 低曝光 | 设置子项 | 不影响日常使用 |

结果:
- 高曝光: 3 个(≤5 ✓)
- 低曝光 + 仅上下文: 8/12 = 67%(≥30% ✓)

如果代理把 20 个全摆一级 nav, 这就是稿子里抱怨的"工程后台病"。

## 与成熟产品对比

3C 验收时硬要求。**不是抄, 是看取舍是否对齐**。

### 对比维度

| 维度 | 检查 |
|---|---|
| 主姿态 | 你的姿态 vs 竞品姿态。一致 = 学。不一致 = 必须有明确差异化理由 |
| 首屏权重 | 竞品首屏放什么 vs 你首屏放什么。差异要可解释 |
| 一级导航 | 竞品有几项 / 你有几项。竞品藏的, 你藏了吗? 竞品露的, 你露了吗? |
| 能力升降级 | 同一能力, 竞品给什么层级 / 你给什么层级 |
| 信息密度 | 同类用户压力下, 你的密度合理吗 |

### 不一致 ≠ 错

竞品和你做不同 = 你做错了吗? 不一定。**关键是有没有理由。**

```
不一致 + 理由清晰    = 合理差异化 ✓
不一致 + 理由含糊    = 多半没想清楚, 需要回去想 ✗
不一致 + 完全没意识到 = 默认套了通用壳层, 必须重审 ✗
```

## 常见 demo 气味清单

3C 验收时逐项扫。出现任一项 = 不通过, 必须修或写明保留理由。

### 视觉层

- 紫色渐变在白底 hero(经典 AI 工具 demo 标配)
- 重复 rounded card 堆叠, 没有视觉主次
- 随机 glow blob 装饰
- 字号梯度跳变(标题 36 → 内容 12, 没有中间档)
- 配色过饱和(saturation 100% 紫红蓝混)
- 微妙阴影 + 大圆角 + 大间距的"通用 SaaS card"
- AI 生成图标(看起来 generic, 没有领域感)

### IA 层

- 一级导航超过 5 项, 全部"功能名"(没有用户任务命名)
- 首页是 "4 KPI 卡 + 8 功能入口" 的工程后台标配
- "设置" 抢一级导航位置(应该是用户菜单子项)
- 每个能力都有独立页面, 没有任何"仅上下文操作"
- 一级导航按字母排序或按实现顺序排序(应该按用户主任务排序)

### 内容层

- Hero 区写"智能 / 高效 / 强大 / 一站式"等空话
- 空态文案是"暂无数据"
- 错误态是"出错了, 请稍后再试"
- 按钮文案是"提交 / 确认 / 取消"
- 表头用英文驼峰(createdAt / userName)而 UI 是中文

### 交互层

- 所有操作都是页面跳转, 没有 modal / drawer / inline edit
- 表格行不可点击, 必须找右侧的 ⋯ 菜单
- 所有按钮都是 primary 紫色
- 无 hover state, 无 loading state, 无 empty state

## 反模式

- 把"产品姿态门禁"当成可跳过的可选步骤
- 选姿态选成"通用 web app" 或 "什么都是"
- 首屏主信号写空话: "突出核心价值 / 展示产品能力 / 让用户感受智能"
- 升降级表把所有能力都标"高曝光"(等于没做升降级)
- 竞品调研敷衍, 只写产品名不写 IA 细节
- 把 demo 气味清单当形式, 实际产物里全是这些气味但 3C 报告写"通过"
- 3C 由实现代理自己审自己 (违反 OMC writer/reviewer 分离原则)
