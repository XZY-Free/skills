# 自治补齐工作流

目标: 把“缺少前置条件”当成交付工作的一部分处理。完整 OPC 任务里，代理默认自己补齐
本地工程、版本控制、验证和预览交付需要的基础设施；只有真正需要用户输入、授权或承担风险
时才暂停。

## 触发场景

- 完整 OPC: 用户说“从需求到上线”“后面都做完”“你决定”“完整交付”；
- 当前目录没有 Git 仓库、`package.json`、前端项目、测试命令、CI/CD、mock 数据或部署配置；
- 中断恢复后发现当前阶段需要的本地前置条件不存在。

## 自治补齐矩阵

| 缺什么 | 默认动作 | 何时问用户 |
|---|---|---|
| Git 仓库 | 在当前业务工作区执行 `git init`，补 `.gitignore`，阶段完成后可做本地里程碑提交 | 已有父级仓库、目录所有权不清、需要推送远端 |
| 前端工程 | 按方案选定框架起脚手架，生成 `package.json`、路由、样式和启动/构建命令 | 框架选择会影响团队约束或用户指定技术栈缺失 |
| 设计风格 | 从行业、PRD、素材和聊天语言推断默认风格，必要时给 2-3 个选择 | 品牌调性、主题、视觉密度会明显影响验收 |
| 数据/API | 建 typed mock、fixture、字段映射表和 pending API 清单 | 需要真实 API key、后端地址、私有数据或合规判断 |
| 测试能力 | 新项目补最小 test/build/browser 验证；现有项目复用已有命令 | 加依赖会冲突、测试环境需要凭证或外部服务 |
| CI/CD | 没有配置时补最小 build/test workflow 或 release checklist | 需要远端仓库、组织权限、付费 runner 或生产审批 |
| 预览上线 | 优先本地 preview 或安全平台 preview，记录 URL/端口和证据 | 需要部署 token、服务器、域名、付费资源或 production |
| 文档/台账 | 自动写 `.opc/` 阶段产物和状态记录 | 不问，除非用户明确只要口头结论 |

## 用户确认门

只有下面情况允许暂停，并且要给选择题或明确要用户提供的值:

- API key、token、secret、私有 URL、服务器地址、账号权限；
- production 部署、远端 push、覆盖已有画布/服务器/数据库、破坏性迁移；
- 付费资源、采购、外部服务开通；
- 法务、合规、客户数据范围、真实 SLA 这类代理无法自证的业务约束；
- 品牌/风格/交互取向会显著影响验收，且无法从上下文可靠推断。

选择题默认格式:

```text
这里需要你确认一个会影响交付物的选择:
A. <推荐项>: <为什么推荐>
B. <备选项>: <适用场景>
C. 自定义 / type something: 你直接写要求。
```

用户选择后立即继续当前阶段；不要把“已收到选择”当成收尾。用户说“你决定”时选推荐项，
把依据写进 Stage Card 或状态台账，然后继续。

## Git 启动规则

- 当前目录没有 `.git/` 且不在父级 Git 仓库内时，完整 OPC 默认执行 `git init`；
- 同时补 `.gitignore`，覆盖 node、构建产物、env、日志、`.opc/state` 中大日志等常见噪声；
- 本地 commit 可作为阶段证据；commit message 记录为什么做这个阶段；
- 没有 remote 时不要要求用户先建 GitHub 仓库；继续本地实现、验证和 preview；
- 远端 push、创建远端 repo、修改受保护分支仍是确认门。

## 状态记录

自治补齐动作写入 `.opc/state/opc-task.json` 的阶段 note 或 evidence:

- 自动创建了哪些本地资源；
- 哪些资源仍 pending，因为需要用户凭证或授权；
- 下一个自动动作是什么；
- 如果暂停，用户回来后代理应该从哪里继续。

错误停点示例:

- “没有 Git 仓库，你先创建好我再继续”
- “没有 package.json，所以不能实现”
- “没有部署服务器，本轮只能结束在设计”
- “等你决定风格后我再开始做，当前先到这里”
