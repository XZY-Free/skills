# 定义阶段对话与确认循环

目标: 把"AI 替用户猜需求"变成"AI 和用户对话把需求聊清楚"。

OPC 流程默认假设用户给的是粗糙业务需求, AI 必须主动暴露自己单方面做的决定、用 ConfirmCard 跟用户讨论、用 dialogue log 记下每轮结论。**定义阶段(intake / requirements / solution / ui-design)不是"写完文档就 mark done"的执行任务, 是几次需求会议**, 答完一轮可能引出新问题就再开一轮, 直到不确定性收敛。

执行阶段(implementation / verification / deployment / calibration)走自治推进, 见各自 reference。

## 核心心智模型

定义阶段的心智模型不是"我写一份文档,你批准":

```text
[ AI 单方面写完 158 行 PRD ] -> [ mark done ] -> [ 进下一阶段 ]
                                  ^
                            用户从没机会修需求
```

是"我和你开几次需求会":

```text
[ AI 列假设 + 问关键决策 ]  <- 用户答 / 修 / 引新问题
        |                            |
        v                            |
[ AI 更新理解, 再列剩余假设 + 问 ] <-+
        |
        ...直到 AI 判断不确定性已收敛(用户对假设没异议、
            关键决策有回答、没有遗留疑问)...
        |
        v
[ 落成本阶段交付物文档(PRD / 方案 / UI Brief) ]
        |
        v
[ mark done, 自动进下一阶段 ]
```

ConfirmCard 是讨论媒介, 不是 gate。AI 抛 + 用户答 = 一轮。问几轮不预设, 像两个人开几次需求会; 用户没主动喊停就接着推进, 但内部讨论没收敛前不要写最终文档也不要 mark done。

## ConfirmCard 模板

每轮 ConfirmCard 最少包含这几段。轮次和粒度按需要伸缩,**不要为了凑结构强行填空**:

```text
OPC ConfirmCard · <阶段名> · 第 N 轮

[我目前对需求的理解]
- 业务目标 = ...
- 核心 framing 翻译 = "<用户原话>" 我理解为含 X / Y, 不含 Z
- 已锁定的事实 = ...

[我替你默认了什么(一句话可改)]
- 数据来源 = 真实接入 + 我自建 Node 后端 + DB
- 后端栈 = Next.js API routes / Hono / Fastify(默认推荐 = ?)
- DB = SQLite(本地) / Postgres(部署) + Prisma
- 部署目标 = ?(必须明确,不允许"或"假设)
- 视觉/品牌 = shadcn/Tailwind 默认
- 测试策略 = lint + typecheck + build + 浏览器主链路
- 主要范围裁剪(如有) = ...

[这轮必须先问你才能继续的硬决策]
- 宿主原生结构化交互可用: 打开真实选择框/确认框/选择工具, 每轮最多 1-3 个问题, 推荐项放第一项
- 宿主原生结构化交互不可用: 降级为 A/B/C/D 文本选项, 每题标默认并保留"自定义 / type something"

[我还不确定但不急的, 下一轮再聊]
- ...

[这轮答完后, 我打算这样推进]
- 把答案落到 .opc/<phase>/<artifact>.md
- 如果你答的同时引出新问题, 我再开第 N+1 轮
- 没新问题就 mark done 并进 <next phase>
```

不是每个字段每轮都必须有。第 1 轮重点抓 framing 解析 + 主要默认假设 + 关键硬决策, 第 2 轮可能只剩 1-2 个具体决策的细化。

## 用户拍板交互面

ConfirmCard 是讨论内容, **不是伪 UI 容器**。当当前 AI 宿主提供真实结构化决策交互(例如 Codex App 的 `request_user_input`、Claude Code / 其它 runner 暴露的 confirm/select/prompt 工具、OMX question bridge 或等价 native UI)且当前模式允许调用时, 必须用它承载用户要点击提交的选择; 不要把普通文本 A/B/C 包装成"选择交互"。

优先级:

1. **宿主原生结构化交互**: 用真实选择框/确认框/选择工具收集硬决策。每轮问 1-3 个问题, 每题 2-3 个选项; 推荐项放第一项并标 `(Recommended)` 或宿主等价推荐标记; 自定义入口依赖宿主 Other 或工具说明。
2. **文本降级**: 只有在宿主原生结构化交互不可用、当前模式不允许调用、或运行面是 API/终端/tmux 且没有 question bridge 时, 才在聊天里列 A/B/C/D。
3. **拆轮而不是长问卷**: 如果第 1 轮有 5 个硬决策, 先问最影响方向的 1-3 个; 其余写进`[我还不确定但不急的, 下一轮再聊]`。用户提交后再开第 N+1 轮。

降级到文本时, 必须明说"当前宿主没有可用结构化交互, 所以降级为文本选项"。这样用户能区分真实选择框缺失和 agent 偷懒。

## 多轮讨论机制

每个定义阶段进入时:

1. **读 dialogue log** — 如果 `.opc/<phase>/discussion.md` 已存在, 先读, 接着上轮聊到的地方继续, 不要从头问。
2. **写 ConfirmCard 第 N 轮** — 开新一轮。N 从 1 开始累加, 用户能看到当前在第几轮。
3. **抛出, 等用户回应** — 宿主原生结构化交互可用时打开真实选择框/确认框/选择工具; 不可用时才发文本 A/B/C。用户答完后, 不要立刻 mark done。
4. **更新理解, 判断是否还有疑问** — 三种情况:
   - 用户答得很具体, 没引出新问题, 也没新假设需要确认 → 进入"落文档 + mark done"。
   - 用户答了但引出新问题(例: "用 Postgres 吧" → "那部署的 Postgres 你有现成实例吗?") → 开第 N+1 轮 ConfirmCard, 只问新问题。
   - 用户给了模糊回应("你看着办 / 都行") → 不要默默选, 把推荐项 + 选不上的理由摆出来, 让用户至少不反对; 这本身也是一轮。
5. **落本阶段文档** — 收敛后写 PRD / 方案 / UI Brief, 把"决策 + 依据 + 讨论日志路径"放进文档头部。
6. **mark done + 进下一阶段** — 不要求用户说"继续"。

## 默认假设暴露规则

每条 AI 单方面做的决定必须列在 ConfirmCard 的`[我替你默认了什么]`段, 满足三个性质:

- **可见**: 在 ConfirmCard 当前轮里能扫到, 不埋进 PRD/方案文档的`风险/缺口/Won't`段落里假装"已声明"。
- **可一句话改**: 用户能说"DB 用 MySQL"/"不要 Tailwind"/"加 RBAC"就改掉, 不需要重开会。
- **有理由**: 每条假设旁标一句为什么默认这个(例: `DB = SQLite — 理由: 单机够用, 部署最简; 想多人协作再换 Postgres`)。

不能埋进默认值、必须列出来的高赌注类目:

| 类目 | 为什么不能埋 |
|---|---|
| 数据来源(真实接入 vs mock) | 决定交付物是"真产品"还是"演示" |
| 部署目标(本地/云平台/自有服务器) | 决定要不要凭证、要不要写 CI/CD |
| 后端栈(Next.js API / Hono / Fastify) | 决定项目结构和依赖 |
| DB 选型(SQLite / Postgres / MySQL) | 决定持久化方式和部署成本 |
| 用户 framing 的字面解析 | "企业级"含/不含 RBAC/审计/SSO 是大笔决定 |
| 测试覆盖策略 | demo vs 真用决定是否值得写测试 |
| 主要范围裁剪(把哪些大模块拆到二期) | 直接改变交付范围 |
| 视觉风格/品牌(无参考稿时) | 影响整个 UI 观感 |

允许埋进执行细节、不必列入 ConfirmCard 的低赌注类目: 小依赖选型(lucide-react vs heroicons)、文件命名、helper 拆法、单文件内的代码组织、mock seed 的具体值、内部路由路径细节。

## 用户 framing 解析

用户常用承诺性词描述需求, 这些词在不同人脑子里含义差距很大。AI 必须把对这些词的解读翻译成具体清单, 在 ConfirmCard 第 1 轮就抛给用户校准。

| 用户原话 | AI 必须翻译成的具体清单 |
|---|---|
| 企业级 | 多租户? RBAC? SSO? 审计日志? 数据导出? SLA? 接口签名? 合规? |
| 完整 / 完整上线 | 包含哪些模块? 端到端可用还是只前端? 真实数据还是 mock? |
| 专业级 / 高级 | 视觉上的高级感(动效/排版) 还是功能完整度? |
| 生产级 / production-ready | 真上线 production 还是仅 preview? 有真实用户访问? |
| 智能 / AI | 真接 LLM/Embedding API 还是 mock 响应? 哪家模型? |
| 数据看板 / 后台 | 真实数据源还是埋点? 多少角色? 实时还是批处理? |
| 小需求 | 真小(单页 + 单接口) 还是用户口里小但其实涉及多模块? |

ConfirmCard 第 1 轮的 framing 解析段是不可省略的, 哪怕用户原话看起来很清楚。**误解 framing 是定义阶段最大的浪费来源**, 它会导致 158 行 PRD 走向错的方向。

## 讨论日志规约

每个定义阶段维护一个 dialogue log: `.opc/<phase>/discussion.md`。追加模式, 不覆盖。

格式:

```markdown
# <阶段名> Discussion Log

## Round N — <yyyy-MM-dd HH:mm UTC>

### AI 抛出
- Framing 解析: ...
- 默认假设: ...
- 硬决策: <问题摘要 + 选项摘要; 若用了结构化输入, 写工具名和提交结果>
- 交互面: 宿主原生结构化交互(如 request_user_input / Claude Code confirm-select / OMX question bridge) / 文本降级 A/B/C / 其它

### 用户回应
> 用户原话粘贴(只摘和需求相关的)

### 由此确定
- ...

### 新引出的问题
- ...(下一轮要问的)

### Round N 收敛状态
- 状态: 继续到第 N+1 轮 / 已收敛, 进 <next>
- 下一动作: ...
```

为什么单独存档不塞进 PRD/方案正文:

- PRD 是给读文档的人看的"最终需求", 讨论日志是"我们是怎么聊到这里的"。混在一起两份文档都难读。
- 会话断了下次 resume 时, AI 读 `discussion.md` 就能从上一轮继续, 不需要用户重讲。
- 用户回头查"为什么当时选了 X 不选 Y", 日志比 PRD 更直接。

state 台账(`.opc/state/opc-task.json`)只记关键节点(第 N 轮收敛、决策摘要、discussion.md 路径), 不存原始对话。

## 推进与收敛判断

判断当前阶段"不确定性已收敛, 可以 mark done 进下一阶段"的信号:

- [ ] ConfirmCard 列的`[默认假设]`用户全部认可或一一改过
- [ ] ConfirmCard 列的`[硬决策]`用户全部明确答过(允许"你决定"+ AI 已写明推荐项)
- [ ] 上一轮答案没引出新硬决策
- [ ] 用户 framing 已经翻译成具体清单且用户认可
- [ ] 本阶段文档(PRD / 方案 / UI Brief)能根据已确定的事实写出来, 不需要再猜

四条满足后 AI 自动: 写文档 → mark done → 进下一阶段。**不要求用户说"继续"**, 但要在 discussion log 的最后一轮明确写"已收敛, 进 <next>"。

hand-off 文本必须按 [handoff-contract.md](handoff-contract.md) 五段结构收尾 (含显式"[下一步]"句式), 跑过 `scripts/handoff-lint.py` 校验通过才 mark done。**不允许只列"剩余风险: a / b / c" 作为收尾**, 这是被禁的反模式。

判断"还要再开一轮"的信号:

- 用户答时引出新问题、新约束、新角色、新模块
- AI 写文档前发现某字段还在猜
- 上一轮抛的硬决策用户跳过了或答得模糊到无法落地

## 反模式

下面这些做法都违反本流程:

- ❌ "用户在 intake 选了 4 题, 进 requirements 直接写 158 行 PRD, mark done"
- ❌ 把单方面决策埋进 PRD `Won't` 列表("AgentOps 不做") 假装"已声明"
- ❌ ConfirmCard 打完直接 mark done, 把用户没反对当成"全部认可"(等价于不问)
- ❌ ConfirmCard 打完等用户说"继续"才进下一阶段(把讨论媒介当 gate)
- ❌ 把多轮讨论纪要直接塞进 PRD 正文(污染最终文档)
- ❌ 第 N+1 轮 ConfirmCard 把 N 轮已经确定的事再问一遍(没读 dialogue log)
- ❌ 用户原话有"企业级 / 完整 / 生产级"等承诺词, AI 没在第 1 轮翻译, 直接按自己的字面理解写 PRD
- ❌ 数据来源默认 mock, 用户没主动说 mock 也没问就 mock 化(等于交了演示版)
- ❌ ConfirmCard 列 5 个默认假设, 其中"部署目标"用了"Vercel 或本地等价"模糊表述
- ❌ ConfirmCard 收尾只列开放风险("剩余风险: a / b / c") 不给行动方案, 违反 [handoff-contract.md](handoff-contract.md)
- ❌ ConfirmCard 末尾没显式写"等你在原生交互提交" / "等你回 A/B/C" 或"我现在做 X", 对话停在用户手里 (agent 因此停止推进)
- ❌ 把硬决策写成"你看呢 / 你定吧 / 看你的"这种开放式问句, 不给具体 A/B/C 选项 + 默认
- ❌ 当前宿主里明明有可用结构化交互, 仍然只在文本里列一大串 A/B/C/D 让用户手打
- ❌ 一轮同时问 5 个硬决策, 因为超过结构化输入容量就退回长文本问卷; 正确做法是拆成 1-3 个关键问题一轮
