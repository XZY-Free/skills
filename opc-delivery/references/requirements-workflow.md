# 需求阶段工作流

目标: 把口语化、模糊、甚至不懂业务边界的输入，变成能驱动设计、实现和验收的 PRD。
需求阶段结束的交付物是需求文档，不是 UI、代码或 prompt。
需求文档也是下一阶段输入，不是默认等待点；用户没有明确暂停或只要文档时，完成后继续进入方案阶段。

## 输入检查

优先从用户原话、会议纪要、已上线需求、接口文档、截图、现有代码和业务规则中抽取信息。
缺信息时只问 blocker:

- 真实业务目标和成功标准不清；
- 用户角色或核心流程不清；
- 数据来源、权限、接口或部署环境会改变方案；
- 验收标准无法判断。

## 需求访谈方式

默认用选择题，不用长问卷。例:

```text
这个需求我按哪种范围整理?
A. 完整上线需求(推荐): 覆盖角色、流程、页面、接口、权限、验收。
B. 快速 MVP: 只覆盖核心流程和最小页面，明确后续缺口。
C. 自定义 / type something: 你直接写范围。
```

用户说“直接做 / 你决定”时，按完整上线需求推进；把自动选择写进 PRD 的“决策记录”。

## JTBD + MoSCoW 门禁

需求阶段默认使用 JTBD 和 MoSCoW，把模糊口语转成可取舍范围:

- Core Job: `当 <场景>，<角色> 想要 <能力>，以便 <业务结果>`。
- Functional job: 用户实际要完成的任务。
- Emotional/social job: 用户想降低的焦虑、提高的掌控感或对外呈现。
- Compensating behavior: 用户现在用什么土办法解决，为什么不够好。
- MoSCoW: Must / Should / Could / Won't；`Won't` 必须写，避免后续偷偷扩范围。

如果用户输入太薄，先问一个会改变 Core Job 或 Must 范围的选择题；不要一次抛长问卷。

## PRD 最小结构

把 PRD 写到用户项目中的 `.opc/requirements/prd.md`，除非项目已有规范路径。

```markdown
# <需求名称> PRD

## 背景和目标
- 背景:
- 目标:
- 非目标:
- 成功指标:

## 用户和场景
- 角色:
- 使用场景:
- 触发条件:

## JTBD
- Core Job:
- Functional jobs:
- Emotional / social jobs:
- Compensating behavior:

## 范围
- Must:
- Should:
- Could:
- Won't:
- 依赖:

## 用户故事
- 作为 <角色>，我想 <能力>，以便 <价值>。

## 核心流程
1. 入口:
2. 操作:
3. 成功结果:
4. 异常/空态/权限态:

## 数据和接口
- 数据来源:
- 关键字段:
- 接口/后端依赖:

## UI/交互要求
- 页面/模块:
- 状态:
- 文案语种:
- 可访问性:

## 非功能要求
- 性能:
- 安全/权限:
- 兼容性:
- 日志/审计:

## 验收标准
- Given/When/Then:
- 必须通过的测试/截图/部署检查:

## Open Questions
- [ ] <问题> | 影响: <影响> | 默认处理: <默认值>

## 决策记录
- <日期>: <决策> | 原因: <依据>
```

## 完成门槛

需求阶段完成必须满足:

- PRD 覆盖业务目标、用户、范围、核心流程、数据、UI、非功能和验收标准；
- 已写 Core Job、Compensating behavior 和 MoSCoW 范围，且 Won't 不为空；
- blocker open questions 已问完，非 blocker 已给默认处理；
- 文案语种和技术词保留规则已写明；
- `.opc/state/opc-task.json` 中 `requirements` 标记为 `done`，并记录 PRD 路径；
- PRD 足以作为方案输入；若用户未说暂停 / 停下 / 只要需求文档，立即进入方案阶段。

如果用户不想要正式 PRD，输出“轻量 PRD”，但仍保留验收标准和 open questions。
