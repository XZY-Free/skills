# 方案阶段工作流

目标: 在 PRD 之后、UI/代码之前，定义“怎么做”。方案阶段不是大而空的架构文档；
它要给 UI 设计、前端实现、API wiring、测试和部署提供可执行输入。

## 进入条件

- 有 PRD、轻量 PRD 或足够明确的需求 brief；
- blocker open questions 已闭合，或已写明默认处理；
- 已检查现有项目结构、技术栈、组件库、接口文档和部署环境。

## 方案探索门禁

默认给 2-3 个方案方向，除非 PRD、现有架构或用户明确要求已经把路径锁死。每个方向写清:

- 适用场景；
- 交付速度；
- 可维护性；
- UI/体验质量；
- 验证和部署风险；
- 推荐结论。

方案不是“想法列表”。选定推荐方案后，把工作切成 planning packet:
discovery、foundation、delivery、verification、follow-through。

## UI 方案门禁

进入 MasterGo/Codify 前，方案必须给出:

- 覆盖范围: 页面、状态、弹窗、抽屉、错误/空态、权限态；
- UI 文案语种；
- 设计方向，或 2-3 个选择项；
- 组件库策略；
- 验证方式。

这些字段要映射进 [design-workflow.md](design-workflow.md) 的 MasterGo 设计 Gate Card。

## 实现方案门禁

进入代码实现前，方案必须给出:

- 使用现有项目栈还是新建项目；
- 目标路由和组件边界；
- 数据来源和字段映射；
- 交互状态和错误处理；
- 测试命令、浏览器验证目标和部署目标。

如果这些信息不完整，先补方案；不要直接写一个无法验收的静态页面。

## 完成门槛

- 方案覆盖 PRD 的 must-have；
- 有 2-3 个方案对比，或写明为何只有一条合理路径；
- 已完成自我审查，没有未标注的占位符或冲突假设；
- 关键风险有处理方式；
- 下游 UI / 实现 / 部署都能从方案拿到输入；
- `.opc/state/opc-task.json` 中 `solution` 标记为 `done` 并记录方案路径。
